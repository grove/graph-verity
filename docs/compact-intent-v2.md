# Compact intent v2

Issue #30 adds a no-model representation and deterministic Rust expander, separate
from `ParserResponse` and `Plan` v1. The schema is
[`schemas/compact-intent-v2.json`](../schemas/compact-intent-v2.json), generated by
`verity_cli schema-compact`. Existing v1 schema output, parser adapters, baseline
configuration, recorded proposals/scores and human-review/holdout gates are unchanged.
The opt-in [v2 model runner](compact-v2-runner.md) is a separate #31 integration;
this document describes the deterministic contract.

## Authority belongs to the request

`Snapshot::compact_context(question, scope, policy, limit)` authorizes the exact
scope and builds an immutable, question-bound context from the snapshot. Its private
fields cannot be replaced through JSON: it implements serialization, not
deserialization. Callers must retain the context belonging to that particular request
and pass that same context to `expand_compact`; the proposal cannot select a context.
This is an API pairing obligation, not model-provided authentication or semantic retrieval.

The context supplies the snapshot ID, sorted named-graph scope, predicate profiles,
bounded row limit, question and indexed vocabulary. Every reference identifies one
**(graph, IRI, role)** tuple. Roles are observed separately in each graph, including
when the same IRI occurs elsewhere with another role. IDs are contiguous unique u16
indexes, assigned in sorted graph/IRI order, then entity/predicate/class order. An
IRI with several roles receives separate IDs; the same IRI in two graphs also
receives separate IDs. Labels are untrusted data. This first implementation includes
the authorized observed vocabulary; it does not infer a question-specific shortlist.

Context construction rejects duplicate/unauthorized scope entries and exceeds neither
the existing request's nor the new context's 128 KiB serialized limit. Narrow the
explicit scope when needed. A model cannot supply an index table or add identifiers.
Repeated use of an existing index for joins is expected; duplicate index definitions
are impossible through this API, duplicate JSON fields fail decoding, duplicate
edges and duplicate projected output names are rejected.

## Proposal semantics

Every proposal is an object with `version: 2` and `proposal`. All fields shown below
are required, including empty arrays. Unknown fields, duplicate fields, unknown enum
values, malformed JSON and integers outside their declared type are errors.

```json
{
  "version": 2,
  "proposal": {
    "status": "candidate",
    "edges": [
      {"from": {"entity": 23}, "predicate": 7, "direction": "forward", "to": {"var": 0}},
      {"from": {"var": 0}, "predicate": 7, "direction": "forward", "to": {"var": 1}}
    ],
    "filters": [],
    "projection": [{"var": 1}],
    "group_by": [],
    "having": []
  }
}
```

These particular IDs belong to the checked-in Norway Schema.org example context.
They must not be reused with another scope/snapshot without inspecting its context.

- Nodes are exactly `{"var": n}`, `{"entity": id}` or `{"class": id}`. Variable
  slots 0–11 become `v0`–`v11`, consistently across edges, filters and projections.
  A shared variable explicitly joins edges; no join or omitted intermediate node is inferred.
- `predicate` is a predicate-role reference. Its graph supplies the edge's graph;
  every entity/class reference on that edge must belong to that same graph.
  `forward` means from → to; `reverse` swaps RDF subject/object. It does not infer
  an inverse property. Class constants are allowed only as rdf:type objects, with
  an explicit class-role index (also for reversed edges).
- A filter is `{"var": 1, "op": "ge", "datatype": "integer", "lexical": "51"}`.
  Operators are `eq`, `ne`, `lt`, `le`, `gt`, `ge`, preserving strict/inclusive
  boundaries. Datatypes are `integer`, `decimal`, `double`, `date`, `date_time`,
  `boolean`, `string`, mapped explicitly to existing XSD types (`date_time` to
  `xsd:dateTime`). Lexical text stays literal data; existing v1 lexical, observed
  range and ordering checks apply. Language-tagged constants, variable-to-variable
  comparisons and literal edge constants are outside v2's compact subset.
- Projection is `{"var": n}` or `{"count_distinct": n}`. Output aliases are
  assigned by projection position: a count at position 1 becomes `c1`.
  Only `COUNT(DISTINCT)` is supported. No implicit projection or aggregate is inferred.
- `group_by` lists variable slots and must exactly match plain projections when
  counts are present. HAVING is `{"count": 1, "op": "ge", "value": 2}`: `count`
  selects a count's **projection position**, not its input variable. Values are u32.

Alternatively, `proposal` is `{"status":"needs_clarification","reason":"..."}`
or `{"status":"unsupported","reason":"..."}`. Reasons contain 1–4096 bytes;
neither status creates a plan or runs a query. These fixtures are not evidence of
model abstention ability.

There are no model-authored graph names, snapshot IDs, IRIs, SPARQL, commands, row
limits, negation, traversal depths, paths, optional joins or other aggregation forms.
Their attempted representation fails strict decoding rather than being dropped.

## Expansion and independent validation

`decode_intent` accepts at most 64 KiB. `Snapshot::expand_compact` checks the version,
context snapshot and current policy, then preserves abstentions or expands a candidate:

1. Apply the existing conservative question preflight for recognized open-world
   negation and ambiguous authorized labels. This is deterministic guarding, not
   model understanding; it cannot detect all linguistic ambiguity or negation.
2. Enforce v1 structural bounds: 1–8 edges/projections, at most 8 filters/group
   slots, 4 HAVING conditions and 12 variable slots. Resolve only trusted,
   graph-local role indexes; reject duplicate edges and class-position errors.
3. Assign variable/count names, map typed literals, and copy snapshot, exact scope
   and limit exclusively from the trusted context into a v1 `Plan`.
4. Call the existing `Snapshot::compile`. It independently checks current policy,
   vocabulary/profiles, connected variable joins, bound outputs/filters, datatype
   compatibility, aggregation and limits. Pattern graphs must exactly cover the
   trusted scope; silently dropping or adding a graph is forbidden.

The result is a normal v1 `Proposal`. Execution still uses `Snapshot::execute`, which
compiles again against the immutable snapshot/current policy. The expander never
constructs SPARQL. There is no route here for executing proposal text as a query.
No missing predicate, class, direction, projection, join, datatype, grouping or
boundary is guessed. Stable rejection codes include `compact_json`,
`compact_version`, `compact_reference`, `compact_duplicate`, `compact_reason`, and
the existing compiler/policy codes such as `scope`, `snapshot`, `datatype`,
`projection`, `variable`, `aggregation`, `complexity` and preflight codes.

## Run fixtures or arbitrary proposals without an LLM

```sh
cargo run --locked -p verity_cli -- schema-compact
cargo run --locked -p verity_cli -- compact-context \
  data/worldcities-transfer/snapshot.nq nquads data/worldcities-transfer/policy.json \
  examples/compact-v2/schema-scope.json examples/compact-v2/schema-question.txt 100
cargo run --locked -p verity_cli -- compact \
  data/worldcities-transfer/snapshot.nq nquads data/worldcities-transfer/policy.json \
  examples/compact-v2/schema-scope.json examples/compact-v2/schema-question.txt 100 \
  examples/compact-v2/schema-two-hop.json
cargo run --locked -p verity_cli -- compact \
  data/wikidata/snapshot.nq nquads data/wikidata/policy.json data/wikidata/scope.json \
  examples/compact-v2/wikidata-question.txt 100 examples/compact-v2/wikidata-two-hop.json
cargo test --workspace --locked
```

`compact-context` prints trusted context for manual inspection. `compact` rebuilds it
from trusted files and executes any supplied compact candidate through the same Rust
boundary, reporting the v1 plan, bindings and graph evidence with fixture origin.
Replace the final path with an arbitrary candidate JSON file, or with
`examples/compact-v2/unsupported.json` / `clarification.json` to exercise abstention.
It never loads a benchmark or case gold.

Source-independent tests cover dates, decimals, direction, joins, bounds, counts,
grouping, abstentions and rejection codes. Hand-authored operations over the retained
public Wikidata and Schema.org snapshots check reference bindings and source-graph
evidence without runtime gold lookup. CLI tests exercise the committed two-hop
conversions and arbitrary input files. Normal CI runs these through the existing Rust
suite and retains pinned Python source/reference checks.

## What this establishes

Compact expansion removes repeated authority fields and long vocabulary IRIs from
proposal output. It can check structural coherence and authorized graph execution;
it cannot know whether a chosen predicate, direction, projection, numeric operator,
entity or grouping expresses the question. A well-typed wrong interpretation can
still execute. Output retains `interpretation_correctness: not_assessed` and
`real_world_truth: not_established`. Reduced generation burden is an experimental
hypothesis, not an accuracy result. No model inference or private holdout is used.
