# Local CPU parser spike (#7)

This is a bounded **development experiment**, using public `dev` and `transfer_dev`
questions and AI-authored reference plans. It is not independently verified Norwegian
accuracy, a locked holdout evaluation, or a Phase 0 feasibility decision. The owner
authorized implementation/inference and this Mac as the development measurement CPU
in the issue #7 implementation request. The owner subsequently approved the exact
experimental budgets and M1 Pro target on 17 October 2026; see the
[pending preregistration](phase-0-evaluation.md#numerical-proposals-approval-and-freeze).
This does not retroactively preregister the development run.

The completed 86-question M1 Pro run, failures and hardware measurements are in
[the development results](../reports/local-parser-development/README.md). The selected
setup was inadequate for unattended Ask despite mostly valid JSON.

## Repeat the experiment

Prerequisites: Python 3.12, the pinned Rust toolchain/dependencies, CMake and a C++
compiler. There are no new Python or Rust library dependencies. From the repository:

```sh
# One-time online acquisition/build, about 1.12 GB of weights plus runtime source:
python3 tools/local_parser.py prepare
cargo build --locked -p verity_cli
# Subsequent runs use only local files, CPU and loopback; choose a fresh output path:
python3 tools/local_parser.py run --out artifacts/local-parser/repeat-1
```

The offline command checks asset/config hashes, regenerates the grammar from the
actual Rust parser response schema, tests the grammar/runtime, starts and owns one
loopback-only llama.cpp process, then runs both public development splits. It does
not fetch data or weights, retry failed questions, rewrite reference plans, or open
the external holdout. Semantic failures are measurements, so a completed run can
exit zero with poor agreement. A runtime, grammar-probe or infrastructure failure
exits nonzero and preserves partial files. A timeout stops inference and the current
experiment; it never leaves a concurrent generation running behind a retry.

The output directory contains `run.json` (hardware, artifact hashes, build receipt,
RSS, probe status and summaries), per-dataset `report.json` and `summary.json`,
server logs, and a directory per question containing the original authorized
request, selected oracle vocabulary, exact prompt, raw runtime response and proposal.
Invalid/truncated responses remain available. Earlier output directories are never
overwritten. The private `verity evaluate-local` stdio protocol is driven by this
runner; it is not an HTTP service or a general executable-tool adapter.

`prepare` writes compiler/CMake versions, build flags and executable hashes in a
build receipt; `run` rejects changed executables and records the receipt, current
CLI/script/benchmark/data/config hashes. Native CPU builds need not be byte-identical
across compilers/platforms. The source archive identifies the runtime revision even
when an archive build's embedded `--version` cannot discover Git metadata. Git
discovery is bounded so it cannot accidentally attribute the runtime to Graph
Verity's parent repository. Every retained source file is checked against the archive;
the generated build-info file is hashed separately.

Every executed proposal still goes through Rust version, snapshot, exact requested
scope, identifier, operator, binding, literal, graph and complexity checks. Only the
existing compiler emits SPARQL. Local-model plans are labeled `local_model`;
manual and fixture origins retain their meaning. Model identity is operator-supplied
by the runner, never taken from model-authored JSON. Results retain
`interpretation_correctness: not_assessed` and `real_world_truth: not_established`.
The old runtime's HTTP compatibility `model` field can default to `gpt-3.5-turbo`;
the owned executable and GGUF hashes, not that field, identify actual local inference.

## Oracle vocabulary and injection boundary

The experiment intentionally measures parsing with oracle vocabulary. For each
public executable development case it selects only the entity/class/predicate
identifiers occurring in the reference plan. Non-executable cases receive all
authorized predicates/classes plus word-boundary label mentions of at least three
characters. Each ID receives at most four deterministic labels (Norwegian first);
predicate profiles are restricted to selected IDs. Rust builds the catalog **after scope authorization**;
the selector asserts that every oracle ID occurs in it. Reference pattern order,
direction, joins, operators, numbers, expected status and answers are not supplied
to the model. Non-executable questions have no reference-plan IDs. This is not a
retrieval experiment, and its results cannot predict performance with missing
retrieval candidates. The original and selected contexts are retained for audit.

Graph labels are quoted JSON data with an explicit instruction boundary. ChatML
sentinels in data are escaped before prompt assembly. This is a defense against
message-boundary injection, not a proof that a model cannot follow malicious text.
Rust authorization remains independent of labels and model behavior.

## Checks and interpretation

Model-free regression tests run in ordinary CI, which continues to download no
weights and invoke no inference. The opt-in experiment additionally performs:

- Exact-runtime grammar validation: valid candidates and each abstention variant;
  rejected malformed/truncated text, raw SPARQL, missing fields, unknown fields and
  invalid enums. **b5046's validator exits zero for rejected text**: the harness
  checks its explicit verdict, covered by a regression test.
- Live unconstrained and constrained generation on the same adversarial prompt,
  plus a malicious RDF label/message-delimiter probe using the production grammar.
  Each completed constrained output is checked by the runtime grammar validator;
  the malicious output is also passed through Rust's independent parser boundary.
- Rust rejection regressions for valid JSON containing unauthorized scope/IDs,
  changed snapshots, datatype mismatches, unsupported plans and raw query fields;
  a schema-valid incorrect numeric operator remains visibly wrong after execution.

`json_valid`, `contract_valid`, `safety_valid`, structural IR equality and exact
answer agreement are distinct fields. All supported questions remain in agreement
denominators, including false abstentions, malformed output and rejections. A safe
abstention is counted separately from a *correct expected-status* abstention.
Wrong-but-contract-valid candidates and successfully executed reference-mismatching
plans are reported separately. Graph execution alone is never parsing accuracy.

Component diagnostics compare operator, direction, predicate, entity, datatype,
number, literal, scope, projection, grouping, limit and snapshot. These comparisons
are deliberately ordered and variable-name-sensitive. Alpha-renamed or differently
ordered equivalent plans can miss structural equality; frozen answer bindings are
scored independently (including their column names). Component counts include
matching empty fields; inspect the question/family when assessing actual numeric or
datatype cases. A `wrong_plan_successful_execution` flag means conservative
structural reference mismatch, not a human adjudication of inequivalent meaning.
Original per-family counts and Wilson intervals for the combined pass count remain
in the Rust report; no small development sample establishes a population error rate.

`generation_ms` includes prompt/artifact handling, tokenization and runtime round
trip. `end_to_end_ms` adds authorized catalog creation, Rust validation, execution
and evidence, stopping before the independent reference query. The legacy
`pipeline_ms` fields still mean only validation/query/evidence. Warm p50/p95/p99
exclude the first case in each new server. Cold first-answer time adds new server
startup and Rust process/snapshot startup to that first case. Warm runs can reuse
the common prompt prefix; runtime token counts disclose the reuse. This is **process cold,
OS page cache not evicted**, not an uncached-disk cold claim. Artifact writing is
inside the measured path. Concurrent host activity and native build flags matter.

RAM reporting includes a 200 ms sampled aggregate RSS for runner, server and Rust
process, plus the OS child-process lifetime high-water mark. Aggregate RSS can count
shared pages twice; samples can miss spikes. It is neither model weight size nor
an isolated incremental-model-memory measurement.

## If the model is inadequate

Do not promote unrestricted Ask based on JSON validity or a successful query. Keep
the existing deterministic path: exact authorized label/IRI resolution, explicit
user-selected typed plans and Rust validation; require user confirmation of a
displayed plan or abstain when intent is ambiguous. This path has no natural-language
accuracy claim and is already executable through `resolve` and `run`. Fixture replay
remains a test adapter. A smaller model is an unmeasured alternative, not a promised
performance fix. Any revised model/prompt needs fresh development measurements and
a frozen setup before a separately authorized one-shot external holdout run.
